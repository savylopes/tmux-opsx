# Design

## Context

Follow-up to `pr-monitor-subagent` (archived). Code: `skills/opsx-pr/pr.sh` (`with_state_lock` ~l.350, `write_seen` ~l.445, `loop_text` ~l.640, `watch_col` ~l.1345), `agents/opsx-pr-monitor.md`. Findings: reviewer F1–F6, security F1–F4, QA F1–F3 (all P2).

## Decisions

1. **`stopped` vs `superseded`.** `cmd_stop` writes `stopped_gen=<new gen>` together with the bump. `wait --gen <n>` on a gen mismatch exits 4 and prints `pr: stopped` when the state's `stopped_gen` equals its current `monitor_gen`, and `pr: superseded` otherwise. `start` and `restart-input` clear `stopped_gen`. The monitor maps exit 4 + `stopped` → `stopped`, and exit 4 otherwise → `superseded`.
2. **Gen-scoped monitor count.** Prompt step 1: "A monitor counts as running only if you started it with `--gen <current>` (the gen in the command below) and it has not returned. Start one when none counts." `superseded` → go to step 1 (it starts one only if none for the current gen is running). `stopped` → start none and say the loop stopped. The old "when unsure, start one" sentence goes.
3. **Slice and calls.** Claude Code moves a subagent's Bash call to the background after 180 s whatever its `timeout` (currently 180 s: a server-side setting, the result says "moved to the background … after running for 180s"; seen in a live PR 48 monitor and in review sessions). So one wait call must end before 180 s, and the 600 s Bash timeout is irrelevant. In `loop_text` for Claude, `s=$(( SLICE > 170 ? 170 : SLICE ))` (min 1) and `calls=$(( 1620 / s ))`, at least 1 and at most 30 (170 s → 9). The monitor's prompt becomes two lines: the command, then `max-calls: <n>`. The agent file reads `max-calls` (default 3 when missing, capped at 30), and the guard ignores it because it is not a command. The `idle` line of the prompt says "about <calls × s / 60> minutes", the effective run, not a fixed 27. Foreground CLIs keep `--slice` as given (default 540).
   - **Wall time of `wait`.** 170 s leaves 10 s for Claude Code's own overhead only if `wait` never runs past its slice. Before, the deadline counted from after setup, and a poll round could start just before the deadline and end a whole round later. Now `cmd_wait` takes its start time before any setup, and after each poll round it starts the next round only when `now + poll + <last round's duration>` is within the deadline; otherwise it sleeps to the deadline and exits 3. So `wait --slice 170 --poll 60` returns within 170 s plus the overrun of one round that takes longer than the one before it.
   - **No early reply.** The agent file says to return nothing before the one final line. If a call is still moved to the background (a slow `gh`, a message delivered to the monitor), the result names the task's output file and says it will notify. The live transcript shows the notification shape: a turn that starts `[SYSTEM NOTIFICATION - NOT USER INPUT]` with `<task-notification>` holding `<task-id>`, `<output-file>`, `<status>` (`completed` or `failed`) and `<summary>Background command "…" completed (exit code 0)</summary>` or `… failed with exit code 3`. It carries the exit code but no output, so the monitor reads the exit code from the summary, and for exit 0 (the `event=` line) and exit 4 (`stopped` or `superseded`) reads the output file with `tail -n 5 <output-file>` (stdout and stderr both land there). The monitor has no blocking tool to wait on a background task (TaskOutput was removed from Claude Code), so waiting for the notification can end one monitor turn: that turn's text must be the fixed line `waiting`, never prose and never a result. A notification is not a new prompt and never yields `error: not a pr.sh wait command` (that check applies to the first message only). The window's prompt says that `waiting`, or any line that is not one of the five results, means the monitor still runs: start nothing and end the turn.
   - **Idle cost.** With 170 s × 9 a monitor run lasts about 25.5 minutes, so an idle window is woken by about 2-3 monitor results per hour (`idle`, then a new monitor), instead of the 6-7 wake-ups per hour measured for PR 48 with backgrounded 540 s calls (each early reply woke the window, which reads its whole ~230k-token context). A call that is still backgrounded is the exception and costs one extra wake-up.
4. **Lock.** `with_state_lock`: if `$OPSX_PR_LOCKED` equals the state file, run directly (re-entrant). Else take the lock for 30 s. With `flock(1)`, use `flock -w 30` on fd 9 of `<state>.lock`. Without it, loop on `mkdir <state>.lockd` every 0.2 s up to 30 s, removing it on exit with `trap`, and break a lock directory older than 120 s: rename it to `<state>.lockd.stale.<pid>` first (only one `mv` of the same directory succeeds), then remove the renamed directory, so two processes cannot both break it and one cannot remove the lock the other just took. On a timeout, print `pr: state lock busy after 30s; writing unlocked` to stderr and proceed. While the lock is held, export `OPSX_PR_LOCKED=<state>`. `write_seen` wraps its body as `with_state_lock write_seen_unlocked`.
5. **Quoting.** `WAITCMD=$(printf '%q wait %s --repo %q --slice %s --poll %s --gen %s' "$SELF" "$PR" "$REPO" …)`, used for both CLIs.
6. **Guard.** `monitor-guard.sh` reads the PreToolUse JSON from stdin (`jq -r .tool_input.command`). It allows only `^<path> wait [0-9]+ --repo <arg> --slice [0-9]+ --poll [0-9]+ --gen [0-9]+$`, where `<path>` and `<arg>` are `%q`-style tokens with no unescaped `;|&$\`()<>` and no newline, and `<path>`, with its backslash escapes removed, is absolute and resolves (`realpath`) to the `pr.sh` in the guard's own directory (the guard is installed next to `pr.sh`). A relative path (`env/pr.sh`) or an assignment prefix (`PATH=/x/pr.sh wait …`) is denied. For the background fallback it also allows `cat <file>` and `tail -n <n> <file>` where `<file>` matches `/tmp/claude-<digits>/<word>/<word>/tasks/<word>.output` with no `..` segment and no other argument. It denies everything else with exit 2 and a reason on stderr. The agent frontmatter gets `hooks: PreToolUse: [{matcher: Bash, hooks: [{type: command, command: <installed path>/monitor-guard.sh}]}]`, and `install.sh` writes the absolute installed path into it. The applier first checks code.claude.com/docs/en/sub-agents.md for frontmatter `hooks` support. If it is unsupported, it reports BLOCKED for 3.1 with the doc quote instead of falling back to something else.
7. **`watch=off`.** In `watch_col`, a `last_event` of `merged` or `closed` prints `watch=off` before the age check. A `last_event` of `stopped` prints `watch=off` only while `stopped_gen` equals `monitor_gen`, that is, no `start` or `restart-input` ran since the stop (both clear `stopped_gen` with the gen bump). After a stop and a new start, `list` shows the new monitor's `watch=<age>s`, and `watch=stale` once it stops polling. Chosen over resetting `last_event` on start, which would blank the event column. A state file from before `stopped_gen` existed shows the age as for any other event.
8. **Install.** The `ops-pr-monitor` install, verify and guard lines move under the existing `--skip-pr` condition. Uninstall removes them without that condition.

## Risks / Trade-offs

- [The guard regex is too strict for a path with spaces] `%q` escapes spaces as `\ `, and the regex allows backslash-escaped characters. The tests cover a repo path with a space.
- [A `mkdir` lock left behind by a killed process] It is broken after 120 s, and the 30 s wait then warns. Between the age check and the rename another process can break and retake the lock; the rename then moves a fresh lock. The window is one `find` call long and needs a crashed holder first.
- [The 180 s limit changes] It is Claude Code's setting, not ours. The 170 s clamp and the `waiting` fallback keep the loop correct if it drops (more wake-ups); a higher limit only leaves headroom.
- [A round much slower than the one before] `wait` can then run past 170 s by that difference; the call is backgrounded and the fallback costs one extra window wake-up.
