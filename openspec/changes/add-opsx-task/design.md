# Design

## Context

See proposal.md (Why). Existing pieces this reuses or mirrors:

- `skills/opsx-review/opsx-review.sh`: the ticket key regex (`ticket_in`), `slugify`, exact-name `session_exists`, and the tracker-MCP reading rules in its SKILL.md.
- `skills/opsx-run/opsx-window.sh`: literal prompt delivery (`send_prompt`, never hand-rolled `send-keys`), per-CLI launch commands (`build_launch_cmd`), and `$TMUX` recovery for Codex.
- `skills/fork/fork.sh`: the per-CLI **normal approval** launch modes used by writable forks (`claude --permission-mode manual`, falling back to `default` on older versions; `codex --sandbox workspace-write --ask-for-approval on-request`; `opencode --agent build`; `gemini --approval-mode default`; Cursor without `--mode ask`).
- `opsx-init.sh`: append-once `.gitignore` handling.
- `claude --help` (2.1.308) confirms `-n/--name`, `-r/--resume <id or name>` and `--session-id <uuid>`.

## Goals / Non-Goals

**Goals:**
- Deterministic parts (key detection, name rules, brief header, gitignore, session create, resume, id capture) live in `opsx-task.sh` and are tested without an LLM. The agent only reads the task, writes the description and proposes a short name.
- One task, one session, one conversation, across reboots.

**Non-Goals:**
- Creating an OpenSpec change. The user runs `/opsx:propose` from the explore session when ready.
- Worktrees. Exploring is read-only, so the session runs in the main checkout. `/opsx-run` makes worktrees later.
- Writing to the tracker (comments, transitions).
- Closing or listing task sessions beyond what tmux already shows. `tmux kill-session -t MED-43` is enough for now.

## Decisions

1. **Session, not window.** Each task gets its own tmux **session** (the user asked for the session name to be the task). Lookups compare names exactly (`session_exists`) and require `@opsx_task_repo` to match the repository root, so a manual `MED-43` session or a same-named task in another repo is never taken over.
2. **Approvals, not bypass.** Unlike `/opsx-run` windows, the user is in the session and talking to it, so the CLI starts in a mode where edits and commands need approval: Claude Code `--permission-mode manual` (`default` on older versions), Codex `--sandbox read-only --ask-for-approval on-request` (writes ask, unlike the writable forks' `workspace-write`), OpenCode `--agent plan` (edits denied, shell asks; the `build` agent runs both without asking by default), Gemini `--approval-mode default`, Cursor in its normal mode. The session is for exploring; the user widens it (OpenCode Tab to build, Codex `/approvals`) when moving on to `/opsx:propose`. *Alternative*: bypass, or the writable forks' Codex/OpenCode modes, rejected because the session reads untrusted ticket text with no gate.
3. **Prompt delivery.** The launch command reads the prompt from a file (`"$(cat <file>)"`), the way `build_launch_cmd` does, so no task text is ever spliced into a command line. The prompt file lives in `.opsx/tasks/.<name>.prompt` (git-ignored with the folder).
4. **Claude ids are chosen, others are captured.** Claude gets a uuid generated by the script (`uuidgen`, else `/proc/sys/kernel/random/uuid`). For the others, `start` notes the launch time and then polls for up to `OPSX_TASK_ID_TIMEOUT` seconds (default 20) for the newest session newer than that time: `opencode session list --format json`, `agent ls`, `gemini --list-sessions`, and the newest `~/.codex/sessions/**/*.jsonl` (id from its first line). The first match goes into `session_id:`. *Alternative*: "resume latest", rejected because all tasks of a repo share one folder. Every CLI-specific parser lives in one function per CLI so a format change is a one-place fix; the tests drive them through stubs.
5. **Resume commands.** `claude -r <id>`, `codex resume <id>`, `agent --resume=<id>`, `opencode -s <id>`, `gemini --resume <id>`, each in the approval mode of decision 2. Only ids of the shape the script records are resumed (uuids for Claude, Codex, Cursor and Gemini; `ses_<token>` for OpenCode), because `claude -r` and others also take a conversation name and a brief may come from a clone. A resume that exits at once (unknown id) leaves the pane with a message, because the session runs the command through a small wrapper that, on a non-zero exit, prints `resume failed, run /opsx-task <name> again to restart from the brief` and clears `session_id:` in the brief, but only when the CLI does not know the id (its session store or listing lacks it; when that cannot be checked, when it exited within 10 seconds). A non-zero exit after a normal session (Ctrl-C, a crash) keeps the id.
6. **Names.** The key comes first. Without one, the agent proposes the words and `name` enforces the rules (`[A-Za-z0-9-]`, 1-30 characters) and allocates `-2`, `-3`… by comparing the brief's `source:`. `source:` is `jira:<KEY>` (or `ticket:<KEY>` for other trackers), `file:<absolute path>`, or `text:<first 80 characters, one line>`; the script normalises every source it is given the same way, and `find --source <s>` returns the task that already has it, so a text or file input finds its task again whatever name the agent would propose the second time.
7. **Brief format.** Four `key: value` header lines, a blank line, then Markdown the agent writes: `# <name>: <title>`, What the task does, Scope (in / out), Acceptance criteria, Links, Unknowns. `brief` and `refresh` rewrite only the part after the header.
8. **Switching.** Inside tmux, `start` and `open` run `tmux switch-client -t =<name>` for the caller's client (found from `$TMUX_PANE`), unless `--no-switch`. The calling conversation stays where it was.
9. **Own helpers, not a shared library.** Each skill folder is installed self-contained into six places. A shared library would need its own install path and lookup, so the few helpers (key regex, session lookup, prompt send) are copied into `opsx-task.sh` with a comment pointing at their origin.
10. **Gemini tag.** The Gemini prompt ends with "run `/chat save <name>`", so the user can also `/chat resume <name>` inside Gemini.

## Risks / Trade-offs

- [Other CLIs' list formats differ from their docs, or change] → id capture is best effort; empty `session_id:` falls back to restarting from the brief, and the README documents the gap. Parsers are isolated per CLI.
- [Two tasks launched within the same seconds on the same CLI could capture each other's id] → capture filters by the session's directory where the CLI reports it, and `start` takes a lock (`flock` on `.opsx/tasks/.lock`) around launch-and-capture.
- [Ticket text steering the explore agent] → text is data, not instructions in the prompt; edits and commands need approval; no bypass.
- [A clone committing `.opsx/tasks` paths as symlinks] → `.opsx` and `.opsx/tasks` must be real directories; briefs and prompts are written to a temp file and renamed; a symlinked brief, prompt, `.lock` or `.gitignore` is refused; the lock is opened for append, never truncated.
- [`refresh` typing into a split shell pane] → the agent pane id is recorded at launch (`@opsx_task_pane`) and `refresh` sends only to it.
- [A user's own session named like a ticket] → refused unless tagged by `/opsx-task` for this repo.

## Migration Plan

Additive: a new skill. Rollback is `install.sh --uninstall` or `--skip-task`. Existing `.opsx/tasks/` folders are left on disk.

## Open Questions

- Real-CLI confirmation of the id-capture formats for Codex, Cursor, OpenCode and Gemini, on a machine that has them (see proposal Open Points). It does not change the specs: failure already degrades to restarting from the brief.
