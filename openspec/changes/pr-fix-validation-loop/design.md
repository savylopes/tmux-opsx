# Design

## Context

The maintain prompt is generated by `prompt_text` in `skills/opsx-pr/pr.sh`. The sections that change are "Events", "You may do on your own" and "Gates before a push". The `/opsx-run` validate dispatcher (`skills/opsx-run/SKILL.md`, "validate") already defines the gate order, the verbatim-findings fix rounds, the `DISPUTE` handling for eval, and the rule that the applier's report is never passed to eval. This change reuses those rules in the PR window rather than inventing new ones.

## Decisions

1. **Mechanical vs. fix round.**
   - Mechanical (window does it, tests only): a rebase or restack with no conflicts, `rerun`, `seen`, the base retarget after a parent merged, replies, `note`.
   - Fix round (validation loop): any edit to tracked files, i.e. a review-comment change, a CI fix caused by the PR, or conflict resolution (mechanical conflicts included, because they still edit code).
   The window may not run `git commit` with its own content changes: on Claude Code, Cursor CLI and OpenCode only ops-applier commits.
2. **Gate selection.**
   - eval: when the head branch is `opsx/<change>` and `openspec/changes/<change>/` (or the change's archive) exists in the worktree, or when the window is a change window. Otherwise SKIP with the reason printed.
   - reviewer and security: always.
   - qa: when `.opsx/preview.yaml` exists, using the same preview steps as the validate prompt. Otherwise SKIP.
3. **Fix-round input.** ops-applier gets:
   - the worktree path and branch;
   - the event kind;
   - the material, quoted as untrusted data under the existing "Untrusted input" rules;
   - the instruction to commit without pushing, with no AI attribution trailers;
   - on re-rounds, the gate's FINDINGS verbatim (F1, F2, …).
   ops-eval gets only the change name, branch and worktree, and any DISPUTE lines.
4. **Round limit.** At most 3 applier rounds per event, counting all gates. Then the window asks the user with the remaining FINDINGS. This is recorded with `pr.sh note`, so it survives a restart.
5. **Push and replies.** These happen only after the loop passes and the tests pass. Pushing stays in the window through `pr.sh push`, because the applier never pushes. A reply cites the commit SHA. A push rejected with exit 5 is still treated as head-moved.
6. **Models.** The gates use their installed agent files; this change adds no per-agent model flags. The monitor's default model becomes sonnet, because haiku misread exit 3 in live windows. The monitor makes about 10 short calls per 27 min, so the extra cost is small next to a window wake-up.
7. **Concurrency.** A fix round runs while the monitor keeps watching. The rule against acting on self-caused events also covers the push from a fix round.

## Risks / Trade-offs

- [Slower, more expensive fixes] A one-line review fix now costs an applier, reviewer and security pass, plus eval for an OpenSpec branch. This is accepted: it is what the user asked for, and mechanical rebases stay cheap.
- [The window is blocked during a long fix round] The user's messages wait until the round ends. This is the same as `/opsx-run` windows today.
